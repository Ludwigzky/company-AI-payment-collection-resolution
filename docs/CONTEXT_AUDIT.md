# 生成上下文审核

生成流程在原有法条检索和适用条件核对之外，增加独立上下文复核。复核使用当前账号、当前案件、当前资料版本及本次选中附件；不拼接其他案件、历史对话或其他账号的信息。

## 流程与边界

1. 输入验证后，先建立未经核实的案件事实清单，检索有限官方法条库并保存完整原文、版本、时间适用提示、官方链接及证据缺口。
2. 生成前检查法律上下文的完整性与来源一致性，包括事实编号、法条编号、条文原文、版本元数据和检索预算。不能用截断原文或模型补写条文弥补缺口。
3. DeepSeek 生成候选补充意见；原有字段、危险指令和法律引用校验继续执行。法律核对正文仍由服务端依据固定核对项组成，不采用模型自写法条或办理结论。
4. 对通过格式校验的候选内容，使用一次全新的审核请求，重新提供本次事实、已检索法律原文、附件内容和候选补充意见。审核覆盖整体研判、推进策略、逐项建议、待确认问题、沟通草稿及材料发现。
5. 审核返回结构化的支持判断，并关联本版本既有事实、法律核对项、条文编号、完整条件与缺口索引。服务端校验覆盖范围与引用，从可信快照组成公开的适用性说明、原文、版本和链接；不采用审核模型另写的事实或法律解释，不接受新法条、新链接或升级后的适用状态。业务协调段也须关联本案事实；法律核对段须关联本项条文；材料段须关联对应材料清单。
6. AI 补充意见仅在审核通过时返回。审核拒绝、引用不匹配、超时或无法完成时保留规则方案和法律条件核对，显示审核状态；不展示或保存被拒绝的候选补充文字。

新上下文请求仍使用该账号配置的 DeepSeek 服务，不代表不同机构或律师进行了独立审查。保存的是面向使用者的适用性解释和证据关联，不保存模型内部思维过程。自动审核通过不等于事实真实、合同有效、法律适用已经确定或案件责任成立。

## 溯源与历史版本

审核记录随方案保存在 `recovery_runs.plan_json.contextAudit`，与该版本的 `legalReview`、填报快照、附件编号及附件校验值关联。上下文标识绑定本次快照、候选内容和每次生成独有的随机量，另保存候选内容摘要校验值；审核响应必须匹配本次标识。即使两个案件内容完全相同，也不能复用彼此的审核响应。

页面和导出展示本版本的审核结果、适用性解释、关联事实与法律依据；法条全文、版本及官方链接来自同一版本已保存的法律核对记录。新的审核时间不替代法条来源的最近核验日期。

既有历史方案未执行新增审核时明确标注，不能补写为审核通过；更新案情并重新生成后，才会形成带本机制的新版本。历史原文和快照不回写。已经下载的文件需重新导出，新增审核本身不能追溯执行在旧模型输出上。

## 预算与限制

单次请求共享最长45秒总预算，最多4次模型调用、候选生成和审核各不超过2次。候选格式错误可修复一次，审核协议错误可修复一次；明确的语义拒绝不能重问同一候选。仅在仍有完整两阶段预算时，允许根据未支持段落重新对照原始材料生成一个不同候选，随后重新全量审核。未改动被拒绝段落、仍有不受支持内容或修复预算耗尽时回退。网络、服务错误、空白或截断响应不自动循环重试。修复可能增加耗时与用量。

候选生成的输出上限为无附件3,000／有附件4,000 tokens，审核输出上限8,000 tokens，包含修复的单次合计上限22,000／24,000 tokens。发出审核请求前，先检查完整结构化答复所需的固定编号与索引；通过scoped-v2短引用绑定完整服务端来源范围，发送时不反复复制同一组长编号；接收时先展开为全部原始事实、条文、条件和证据缺口，再执行原有逐项校验。预计短引用协议的必需答复超过7,500个ASCII字符时，明确按审核预算不足回退，不通过删减必要法条、漏审段落或截断结果来通过审核。减少选中材料或拆分待核查事项后可重新生成。

当前法律库仍是有限的官方法条快照，不是实时全库检索。审核可以发现部分不一致与缺乏依据的问题，但不能证明没有遗漏其他法律、历史版本、司法解释或地区及行业特别规则。证据真实性、完整性及最终法律判断继续由人工核实。内部跟进备注和应收总览不会因此自动并入模型输入；需要纳入分析的进展仍应更新基本案情或选中相应材料。

接口采用 DeepSeek 官方支持的 JSON 输出形式，并在服务端进一步检查完整性和字段。JSON 格式正确不表示内容正确；空白及截断响应必须拒绝。参考：[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)、[Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)。
