# 案件与附件存储

本轮实现按登录用户隔离的回款案件工作台：案件基础资料、附件、生成历史和跟进记录统一绑定到案件。新存储为空，不写入示例或真实案件。当前没有企业成员、角色、部门授权或跨用户共享案件功能。

## 数据模型

| 表 | 内容与关系 |
| --- | --- |
| `recovery_records` | 用户归属、案件编号、名称、active/archived状态、当前revision、白名单基础资料JSON、创建和更新时间 |
| `recovery_attachments` | 用户及案件归属、文件名、实际MIME、大小、SHA-256、私有对象key、创建时间及removed_at软移除标记 |
| `recovery_runs` | 用户及案件归属、生成时revision、独立输入快照、附件ID清单、完整方案、材料读取摘要及创建时间 |
| `recovery_notes` | 用户及案件归属、跟进正文及创建时间；采用追加记录 |

附件、方案与跟进记录都用`(owner_id, record_id)`复合外键关联案件；索引包含用户和案件维度。ID由服务端生成UUID，案件编号使用上海日期及UUID短码，时间戳保存为UTC ISO字符串。

草稿允许不完整资料，例如空到期日、空问题说明及空金额。保存只接受已有基础字段；任意owner、密钥、模型或endpoint字段均被拒绝。生成方案时再检查正金额、有效到期日和问题说明等分析条件。

## 本地与托管存储

本地服务需要Node.js 24，使用`node:sqlite`实现D1接口适配；默认将数据库写入`.local-data/records.sqlite`，原始附件写入`.local-data/files/`。这些目录已加入Git忽略清单。正常重启本地服务会保留数据，删除本地数据目录会使本地记录及附件丢失。

`createLocalStorage({ memory: true })`供测试使用，数据库和附件均只在进程内存在。测试不会向真实托管资源写入案件。

托管Worker使用`env.DB`的D1数据库和`env.BUCKET`的R2对象存储；`.openai/hosting.json`声明`"d1": "DB"`与`"r2": "BUCKET"`。文件内容不写入D1，D1保存归属及元数据，R2保存原始字节。发布需要同时保留资源绑定与数据库迁移，构建成功本身不证明线上迁移已经应用。

## 身份与访问边界

线上API从托管平台提供的`oai-authenticated-user-id`头读取身份。该头必须由可信入口注入并防止客户端伪造；不能将本Worker直接暴露到允许任意客户端自行指定这个头的入口。没有身份时拒绝案件操作。请求JSON不能指定owner。

本机预览由Node服务内部注入固定`localOwnerId`，只监听回环地址；这提供单个本机预览身份，不是账号登录或企业权限系统。

案件列表按owner过滤；单案件读取、更新及关联查询同时约束owner与案件ID。单附件操作还约束附件ID，单方案读取还约束方案ID。其他用户或其他案件的附件ID返回404，不能用于下载或生成。

R2对象key由服务端根据用户摘要、案件ID和随机ID生成，不依赖原文件名；同名文件分别存储。浏览器只收到附件ID及展示元数据，下载通过受控内容接口完成。仅服务端的`getAttachment`提供私有对象key；记录与方案序列化会移除`objectKey`及`object_key`字段。

## 版本、并发与生成历史

案件从revision 1开始。基础资料、名称、状态更新，以及附件添加和软移除，都会提升revision。更新资料必须提交读取时的revision；版本已变化时返回409，避免旧窗口覆盖新内容。

附件的条件插入与版本更新放在同一个D1 batch中；限制为每个文件5MiB、每案件最多8个有效附件、累计16MiB。并发请求不能共同消耗同一个剩余名额。一次分析最多读取12MiB选中材料。跟进记录和方案保存只更新更新时间，不提升基础资料版本。

分析开始时要求案件未归档且请求revision与当前版本相符。服务端按用户、案件和附件ID取得元数据，读取原始字节并核对大小和SHA-256后，才构建材料上下文。模型请求不接收其他案件附件。

每次生成保存独立的输入快照、选中附件ID、方案与材料摘要，不回写当前input。生成期间切换案件、编辑资料、移除附件或归档案件，完成结果仍归入原案件；旧版本结果用`snapshotStale`明确标记。归档后不能新发起分析，但先前已开始的生成可以追加历史结果，不能因此恢复案件状态。

进程内的`activeAnalyses`阻止同一实例同时生成同一案件；它不是跨Worker实例的全局任务锁，也不是持久任务队列。跨实例的历史写入仍通过D1归属和版本条件保护。

## 软移除与失败留存

归档案件只改变status，不硬删除案件、方案或跟进记录。移除附件只设置removed_at；默认列表、下载和新分析不再提供该附件，历史快照中的附件ID仍保留，R2原件不随之永久删除。

上传先完成文件校验和对象写入，再登记D1元数据。能确定元数据未写入的校验、配额或归属错误会尝试清理本次新对象。数据库应答不确定时保留对象，避免删除已经登记的文件；出现错误后应重新读取案件确认是否保存成功。当前没有自动清理孤立对象、保留期到期删除或完整备份恢复功能。

## Schema与迁移

Schema定义位于`db/schema.js`，Drizzle配置位于`drizzle.config.js`。在修改schema后执行：

```powershell
npm run db:generate
```

将生成的`drizzle/*.sql`、`drizzle/meta/_journal.json`和snapshot一并保留。初始迁移为`0000_military_nomad.sql`，只建表、索引及约束，不写入案件数据。已有环境应追加迁移，不通过编辑已应用的迁移重建数据库。

本地服务在启动时按journal顺序应用尚未执行的迁移，并记录到本地`_local_migrations`表；请求处理过程中不执行建表。线上部署时需按托管数据库的迁移流程应用相同schema，并核验案件保存、重新读取和附件下载。

持久化测试覆盖用户及案件隔离、乐观锁、并发附件配额、软移除、历史快照、归档期间完成和磁盘数据库重开。API集成测试另覆盖实际本地D1/R2适配、材料归属及上传应答不确定时的文件留存。
