# 法条检索与适用条件核对

本功能在生成每个案件方案前，从应用内已核对的官方法条集检索完整条文，再将案件填报、程序条件与证据缺口逐项对应。它提供可检查的法律依据链，不将模型文字或勾选材料当作已查明事实。

当前收录5份规范文件的24条完整条文；单次最多16条、12,000个条文原文字符，必要条件优先于补充上下文。预算不足会列明缺失条文并降级为依据不足，不截断原文。

## 处理流程

1. 将付款请求、履约或质量异议、争议解决程序、时效核查及特定投诉渠道拆成检索任务。
2. 按任务主题、条文内容与必要前提召回有限条文，记录查询、条文编号和检索预算；不把整个知识库送入模型，也不截断条文原文。
3. 每个法律核对项保存关联事实编号、候选条文原文、法律版本、生效日期、官方全文链接、定位信息、来源核对日期、适用理由、条件和待补证据。
4. DeepSeek 读取相同的事实与法律上下文。法律核对事项必须引用本轨核对项的固定 `basisIds`；不存在、跨轨、重复或指向排除路径的引用将使模型输出回退。法律正文和补证任务由服务端根据核对项组成，不展示模型自行编写的法律建议。模型不能填写或改写法条原文、版本和官方链接；自由文字中的办理指令和确定性法律判断另做保守拦截，该文字防护不等于完整语义审查。
5. 法律核对结果与本次输入、附件和方案一起归入现有 `recovery_runs.plan_json` 快照。切换案件或更新法条集不会改变旧版本中的原文和结论；旧方案没有该数据时提示重新生成。

## 状态含义

| 状态 | 含义 |
| --- | --- |
| 条件性建议 | 检索到相关规范，仍须核对事实、日期、合同和原件，不能据此认定责任成立 |
| 依据或信息不足 | 缺少决定性条件、历史版本覆盖或必要条文，只能补证、核验或咨询法务 |
| 当前条件不适用 | 填报条件触发明确排除项，保留理由和条文，不将该路径推荐为可办理 |

全部事实注明用户填报或材料清单、未经核实。勾选“已有合同”等只表示用户报告持有资料；上传、提取或模型识别均不证明合同真实、债权成立或证据可采。材料发现可辅助下一轮补证，不能自动提升法律适用状态。

## 时间和版本

补充条件可填写合同签订日、本次主张的法律事实发生日及仲裁协议订立日。填报日期仅帮助检查所载版本范围，仍需核对原件、多次履约和完整事件时间线。付款到期日用于内部跟进排序，不等同于这些日期或程序受理日。缺少必要时间时，系统明确保留法律适用疑问，不依据逾期天数直接判断诉讼时效，也不将现行法自动用于历史事实。历史日期超出已载版本时须补检旧法和衔接规则。

本期是有限法条集检索，不是国家法律法规数据库实时全库检索；完整历史版本、地方规则、行业特别规则以及合同效力审查尚未覆盖。来源范围和逐条版本记录见 [法律来源记录](LEGAL_SOURCES.md)。官方链接为已核对的全文页面，具体条文通过条号定位；没有编造条文直达锚点。

## 界面与归档

“回款方案”下的“法律依据”页提供完整依据链、缺口和检索记录。维修安排、对账和内部协作时限单独标为业务建议；它们不因关联法律条件核对而变成法定要求。文本导出与打印包含法律核对快照，官方原文和版本随方案留存。

没有新增公共案件接口、数据库迁移或跨案件上下文。模型或外部服务不可用时，已完成的本地法条检索与条件核对仍随规则方案保存。

## 本轮验证

自动测试覆盖逐条原文元数据、检索预算、历史／未来／无效日期、勾选材料不能证明事实、程序及投诉排除条件、模型跨轨引用与确定结论拦截，以及案件快照重新读取。独立组合检查覆盖1,620组输入，引用快照与语料逐字段一致。此类技术检查不代表真实案件法律准确率或律师审查结果。

本轮浏览器访问被已保存的权限设置阻止，未完成新界面的实际视觉验收，也未新增线上测试案件或再次调用真实模型做本轮验收。前端沿用现有组件与配色，语法、DOM构造及文本导出逻辑已检查；部署状态以站点发布结果为准。
